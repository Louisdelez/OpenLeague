# Publication de la préparation RADS processus/CRT

Publication préparée, non exécutée par son auteur. Entrées figées : manifeste natif `de3171f52c7387491f4be3883996bbee71209270f3f64293ae4679a85ba1c71c` (55 fichiers), audit statique `a09060fecef18a5f4ad7b639cccf9bb349e762db451a6cc5374ed233e906250f` (5 fichiers), revue finale `64f3041a4f00a1a102ba3c98cdaf07140a44d6eca42e15ee156a4a2eb5f05de8` (2 fichiers). Les trois manifestes et les trois fichiers de publication portent l'archive à 68 fichiers.

L'empreinte de l'audit est celle des 1854 octets physiques CRLF. L'ancien `f08e3142b01e933efd9467a1d2a1b3e897b837988e742f5bc0a79e568b48bda7` correspond aux 1804 octets normalisés LF. L'erratum est conservé sans modifier l'audit figé.

`prepare()` est strictement en lecture seule. `main()` demande explicitement le SHA du manifeste natif final avant toute publication. Ni import du script ni lecture des preuves ne lance une sonde, un client ou une compilation.

La publication prépare et relit tous les fichiers dans un répertoire temporaire de `docs`, revérifie les entrées et les documents existants, puis conserve une sauvegarde horodatée. L'archive complète est renommée avant les documents ; le reçu est publié en dernier par remplacement atomique. En cas d'exception, seuls les chemins effectivement visés par cette transaction et contenant encore ses octets sont restaurés. Une modification étrangère détectée n'est jamais remplacée par une sauvegarde obsolète. Les archives temporaires et sauvegardes sont gardées pour diagnostic. Il n'y a aucune suppression récursive ni promesse d'atomicité multi-fichiers en cas de panne machine. La comparaison avant remplacement ne constitue pas une exclusion d'écrivain concurrent dans cet intervalle.

Le plan conserve 24 domaines, 114 tâches et 37 exigences supplémentaires, les anciens résultats, la preuve du vrai client fermé proprement, les 1178 ressources importées, l'état actif et la préférence de communication. Les domaines 02 et 17 reçoivent uniquement un lien de preuve ; aucun statut de tâche/domaine n'est clôturé.

Deux profils explicites utilisent les mêmes dix générateurs : environnement vide et trois variables contrôlées, aucun argument de partie ou environnement hôte importé. Ils atteignent la vraie frontière `HeapReAlloc` sur le tampon atexit de 128 vers 256 octets. Les retours natifs DLL lowIO/argv/environnement valent 0 ; cinq initialiseurs C et 45 C++ sont revenus, le 46e C++ est interrompu. Les 300 contrôles conservés se décomposent en 287 statiques/adaptateurs et 13 contrôles de la primitive SList x86 courante de Windows, sur trois profils distincts ; aucun nouveau test Rust. Les 15 contrôles de synchronisation isolés ne prouvent pas une création de ces objets dans les traces finales.

Avant le nettoyage hôte : 19043 adresses distinctes dont 5426 dans la DLL pour le profil vide ; 19127 dont 5514 pour le profil contrôlé. Les propriétaires hôtes sont retirés, mais 959/962 blocs émulés restent sans destruction native. L'état demeure `attaching` : aucun retour process-attach, DllMain utilisateur non atteint, aucun handle publié ni RadsInitialize. INI8B0630 est entré sans retour ; le fournisseur, l'intégration Rust et le rendu restent incomplets. Les dix tentatives antérieures sont archivées comme diagnostics de leurs propres révisions.
